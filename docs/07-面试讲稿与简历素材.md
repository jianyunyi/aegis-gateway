## 一、项目一句话定位（30 秒电梯陈述）

> **AEGIS 是一个企业级大模型网关（LLM Gateway）**：所有业务线通过它统一接入多家大模型，获得**鉴权、限流、计费、可观测、成本优化、模型评测**六大能力。我独立完成了从需求分析、架构设计到开发的完整闭环，目前已在本地 Docker 环境一键部署运行。

## 三、三大亮点（面试主菜，每个可讲 3 分钟）

### 亮点 1：OpenAI 兼容网关 + 流式架构（讲"为什么 Go"）
- 对外完全兼容 OpenAI 协议 → 任意官方 SDK 改 base_url 即接入，零改造
- 流式转发用**逐块透传（O(1) 内存）**而非全量缓冲 → 首字延迟（TTFT）被记录并入库
- 选型理由：SSE 是 IO 密集，Go 的 goroutine 模型在千路并发下内存优势明显；单二进制部署契合 Docker
- **数据支撑**：压测 200 并发下网关自身转发开销 P95=60ms、RPS≈5700，全链路 0 失败

### 亮点 2：计费一致性设计（讲"为什么不会多扣/漏扣"）
- **先扣后结 + 定时对账**（ADR-005）：Redis 计数做配额预检的快速路径，MySQL 流水是事实来源
- 每 5 分钟对账：发现 Redis 计数与 MySQL used_tokens 不一致时**以 MySQL 为准**纠正
- **演示过的场景**：人为把 Redis 计数改成 999，对账后自动纠正回 132
- 追问预演见下文"计费一致性"

### 亮点 3：成本优化三件套（讲"降本增效"）
- **语义路由**（ADR-006）：显式 Header > Key 默认模型 > 启发式选档（关键词/长度），先规则后 LLM——可解释、零额外成本，LLM 分类器作为扩展点
- **请求缓存**：相同请求直接命中，cost=0；缓存键含实际路由模型，避免跨模型错配（这是踩坑后修复的）
- **预算降级**：月度预算超限自动切到最便宜模型并告警
- **实测数据**：同质量分下 mini 模型成本仅为标准模型的 **28%**（评测飞轮验证）

## 四、追问预演（Top 20）

### 代理与流式
1. **为什么要兼容 OpenAI 协议？** 生态红利：任何 SDK 零改造接入；上游各家（DeepSeek/通义/豆包/Ollama）都兼容该协议，转换成本最低。
2. **流式怎么实现的？** 读上游响应逐行解析 SSE，写入客户端后立即 Flush；用 bufio.Scanner + 4MB 缓冲处理长行；客户端断开（用户取消）与上游错误分开记录。
3. **TTFT 怎么测的？** 记录从收到请求到写出第一行 SSE 的时间，入库 usage_logs.ttft_ms。
4. **上游超时怎么办？** 网关级 UpstreamTimeout 配置（默认 180s）；流式中断时向客户端发 SSE 错误并正确结束连接。
5. **如何支撑计费？** 流式请求自动注入 `stream_options.include_usage`，从结束块解析 usage。

### 鉴权与安全
6. **API Key 怎么存？** 只存 SHA-256 哈希 + 展示前缀（ADR-007），明文仅在创建时返回一次；泄露库也不泄露 Key。
7. **上游提供商 Key 怎么存？** AES-256-GCM 加密落库，密钥由网关 master secret 派生，代理调用时才解密。
8. **限流算法？** Redis Lua 原子脚本实现令牌桶（每 Key 可配 rps/burst），避免"读-改-写"竞态；Redis 不可用时 fail-open 保可用性（生产可切 fail-closed）。

### 计费一致性
9. **为什么用 Redis 计数而不用 MySQL？** 高并发扣减，Redis INCR 原子且快；MySQL 做流水与对账。
10. **对账怎么保证不丢？** 定时任务比较 Redis 计数与 MySQL used_tokens，不一致以 MySQL 为准重设；任务幂等（按 request_id 去重）。
11. **配额超了怎么办？** 预检返回 429 + 明确错误码（42902 quota_exceeded），并落一条失败日志。

### 成本优化
12. **启发式路由的准确率怎么保证？** 可解释、可离线测试；复杂意图通过 Header 显式指定或 Key 默认模型兜底；LLM 分类器作为扩展接口预留，等数据积累后再启用。
13. **缓存一致性？** 缓存键 = 实际路由模型 + 完整请求体，杜绝跨模型错配；TTL 可配（默认 600s）；命中时 cost=0 但 token 计入统计。
14. **预算降级会不会影响体验？** 超限后降级到最便宜模型而非拒绝服务，并打 WARN 告警；可在后台调高预算。

### 评测与观测
15. **评测怎么做的？** 真实调用日志采样（分层按模型）→ 人工打标 → A/B 回归：两模型分别回答全部样本，LLM-as-judge 打分（扩展点，可配 judge 模型），汇总质量分/成本/延迟报告。
16. **大盘有哪些指标？** 今日请求量/成本/Token/成功率/平均延迟 + 7/30 天趋势；调用日志全字段可查（TTFT、路由方式、缓存标记、错误码）。
17. **日志表数据量大怎么办？** 索引按 (api_key_id, created_at) 与 (model_name, created_at) 设计；billing_daily 预聚合表做归档（面试可引深：分表/归档策略）。

### 架构与工程
18. **为什么选 Go？** 流式代理 IO 密集场景 goroutine 优势；单二进制部署；与 Redis/MySQL 生态成熟。
19. **项目怎么保证质量？** 分层 handler→service→repository→model；统一错误码；评审 Checklist；Go 单测（routing/cache/budget/proxy）+ 前端 build 通过；压测报告记录 P95。
20. **部署方式？** Docker Compose 一键启动（网关/后台/MySQL/Redis/mock 沙箱）；离线镜像构建（宿主机交叉编译 + alpine 运行时）；CI 流水线 lint+test+build。

## 七、诚实边界（面试被追问时主动说明）

- mock 上游为演示沙箱，评测分数当前是启发式兜底（LLM-as-judge 扩展点已预留）
- 限流组件在 Redis 故障时 fail-open（生产可切换 fail-closed，属配置决策）
- prompt_preview 仅截断未脱敏（企业版需接脱敏，风险登记册 R6 有记录）
- Windows 单进程压测受 TCP backlog（~200）限制，生产建议 Linux/反代（测试报告已记录）
