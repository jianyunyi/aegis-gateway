## 1. 设计目标与约束

- 目标：实现 PRD 全部 MUST + 优先 SHOULD，架构可水平扩容、可演示、可深讲
- 约束：Go + Gin + Gorm + Redis + MySQL + Next.js + React + TS；本地 Docker 部署
- 原则：
  1. **兼容优先**：对外协议完全兼容 OpenAI，生态红利最大化
  2. **无状态网关**：网关层不落状态（除缓存），状态在 Redis/MySQL，支持水平扩容
  3. **流式优先**：任何长耗时调用必须流式返回，禁止全量缓冲
  4. **可观测内建**：每个请求生成 request_id，全链路可追踪

## 2. 总体架构

```
                        ┌─────────────────────────────┐
                        │   管理后台 Web (Next.js)     │
                        │  大盘/Key/模型/日志/账单/评测 │
                        └──────────────┬──────────────┘
                                       │ JWT + REST (/api/v1/admin)
       业务方 (OpenAI SDK / curl)      │
        ───────────────────────────────┤
        Authorization: Bearer ak_xxx   │
                                       ▼
   ┌───────────────────────────────────────────────────────┐
   │              AEGIS Gateway (Go / Gin)                  │
   │  Middleware链:  KeyAuth → RateLimit → Sanitize(脱敏)   │
   │                → Route(语义路由) → Proxy(流式代理)      │
   │  Service: 计费 / 缓存 / 预算 / 日志 / 评测采样           │
   └───────┬──────────────────────────┬────────────────────┘
           │                          │
      Redis(限流计数/配额/           MySQL(用户/Key/提供商/
      请求缓存/预算计数)              模型/调用日志/账单/评测)
           │                          │
           ▼                          ▼
   ┌─────────────────────────────────────────────┐
   │ 上游模型: OpenAI / DeepSeek / 通义 / Ollama  │
   │ (统一 OpenAI 兼容协议接入, 可插拔 Provider)   │
   └─────────────────────────────────────────────┘
```

**核心链路时序（流式对话）**：

```
调用方                Gateway                         Redis            MySQL            上游模型
  │ POST /v1/chat/completions (stream)                 │                │                 │
  ├─► KeyAuth: 哈希比对 Key ──────────────────────► 查 key_hash 状态    │                 │
  ├─► RateLimit: Lua 原子取令牌 ──────────────────► 令牌桶            │                 │
  ├─► Sanitize: body 脱敏                            │                │                 │
  ├─► Route: 规则/启发式选模型 ──► 预算检查 ──────► 当日成本计数        │                 │
  ├─► Cache: hash(prompt+model) 命中? ──────────► GET pc:{hash}       │                 │
  │        ├─ 命中 → 直接返回缓存流 (标记 cached)     │                │                 │
  │        └─ 未命中 ────────────────────────────────┼────────────────┼──► POST (stream)
  │  逐块转发 (io.Copy + 进度回传) ◄──────────────────────────────────┼── SSE chunks ◄─┤
  │  结束时: 统计 usage 回包 ───────────────────────► 扣费 + 写 usage_logs │ 记日志      │
  │  缓存回写 (TTL) ───────────────────────────────► SET pc:{hash}    │                 │
```

## 3. 关键架构决策（ADR）

### ADR-001 用 Go 实现网关，而非 Node/Python
- **决策**：Go + Gin 实现代理核心与所有服务。
- **理由**：SSE 流式转发是 IO 密集，Go 的 goroutine 模型在千路并发下内存占用远低于 Node/Python；单二进制部署天然契合 Docker；Gin 中间件模型与网关中间件链一一对应。
- **代价**：AI 生态库不如 Python 多 → 核心能力（代理/限流/计费）本就是网关自研，不依赖生态。

### ADR-002 对外兼容 OpenAI 协议，而非自研协议
- **决策**：代理侧实现 OpenAI 的 `/v1/chat/completions` 等接口。
- **理由**：OpenAI 协议是事实标准，任何官方 SDK 零改造接入（满足 B1）；上游各家均兼容 OpenAI 协议（DeepSeek/通义/豆包/Ollama 均可），请求/响应转换成本最低。
- **代价**：OpenAI 非标准能力（如某些厂商扩展字段）需透传处理。

### ADR-003 流式转发逐块透传，禁止全量缓冲
- **决策**：上游响应通过 `io.Pipe` 逐块转发给客户端；同时并行统计 usage。
- **理由**：全量缓冲会导致首字延迟=整个响应时长，违背流式体验；逐块透传内存 O(1)。
- **代价**：错误处理复杂——上游中断时需要向客户端发 SSE 错误事件并正确结束。

### ADR-004 Redis 管状态，MySQL 管持久化
- **决策**：限流计数、配额、请求缓存、当日预算计数放 Redis；Key/用户/模型/日志/账单/评测放 MySQL。
- **理由**：Redis 原子操作（Lua 脚本）支撑高并发限流与扣减；MySQL 保证计费与日志的持久性、可查询性。
- **代价**：Redis 与 MySQL 一致性需对账兜底（见 ADR-005）。

### ADR-005 计费采用"先扣后结 + 定时对账"
- **决策**：调用完成后 Redis 原子扣减配额并写 usage_logs；定时任务（每 5 分钟）汇总 Redis 计数与 MySQL 流水对账，发现不一致以 MySQL 为准补偿。
- **理由**：Redis 扣减快但可能丢（重启/过期）；MySQL 流水是全量事实。对账保证最终一致，能讲清楚"为什么不会多扣/漏扣"。
- **代价**：对账任务需要幂等设计（按 request_id 去重）。

### ADR-006 语义路由先规则+启发式，LLM 分类后置
- **决策**：M4 的路由实现为：(a) 显式指定（header/参数强制模型）；(b) 规则（用户/Key 级默认模型）；(c) 启发式（任务关键词、prompt 长度、语言检测）分流便宜/标准/强模型。LLM 分类器作为扩展点预留。
- **理由**：规则可解释、零额外成本、可离线测试；LLM 分类每次多一次模型调用，成本与延迟收益需先有数据支撑（这正是评测飞轮该回答的问题）。
- **代价**：复杂意图分类能力有限 → 预留 `Router` 接口，后续可插拔 LLM 实现。

### ADR-007 Key 只存哈希，明文只在创建时展示一次
- **决策**：生成 `ak_` + 32 位随机串；DB 存 SHA-256 哈希 + 前 8 位前缀（便于后台展示 `ak_3f9a...`）。
- **理由**：数据库泄露不导致 Key 泄露；前缀便于人眼识别。
- **代价**：Key 丢失无法找回，只能重新生成（符合安全惯例）。

## 4. 技术选型清单

| 组件 | 选型 | 理由 |
|---|---|---|
| 后端 | Go 1.22+ / Gin | 高性能、中间件模型契合网关 |
| ORM | Gorm | 与 MySQL 集成成熟，支持迁移 |
| 缓存/计数 | Redis（go-redis） | 原子 Lua 脚本、TTL、pub/sub 通知 |
| 数据库 | MySQL 8 | 关系数据 + 日志查询（演示环境可用 MariaDB 兼容镜像） |
| 前端 | Next.js 14 App Router + React 18 + TS | SSR 后台 + 图表（ECharts） |
| UI 组件 | Ant Design 5 | 企业后台主流，表格/表单开箱即用 |
| 指标 | Prometheus + Grafana | 标准可观测栈 |
| 部署 | Docker Compose | 一键启动；Dockerfile 分阶段构建 |
| 鉴权 | JWT（后台）+ API Key（代理侧） | 双层鉴权模型 |
| 日志 | slog 结构化 JSON | 标准库、低开销 |

## 5. 数据库设计

### 5.1 关系模型（ER 概览）

```
users 1──n api_keys 1──n usage_logs
providers 1──n models

usage_logs ──> billing_daily (按日聚合, 冗余可重建)

eval_datasets 1──n eval_runs
```

### 5.3 Redis Key 设计

| Key | 类型 | 说明 |
|---|---|---|
| `rl:{key_id}` | token bucket（Lua） | Key 级限流 |
| `rl:global:{ts}` | ZSET | 全局滑动窗口防刷 |
| `quota:{key_id}` | STRING 计数 | 剩余配额（负数=超限） |

## 6. API 契约

### 6.1 代理侧（OpenAI 兼容，Bearer `ak_xxx`）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/chat/completions` | 对话（支持 stream SSE） |
| POST | `/v1/completions` | 补全 |
| POST | `/v1/embeddings` | 向量化（透传） |
| GET | `/v1/models` | 可用模型列表（网关自有目录） |
| GET | `/healthz` | 健康检查 |

请求/响应格式与 OpenAI 完全一致（透传 + 网关附加 `x-request-id` 响应头）。

### 6.2 管理侧（REST，JWT）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/admin/auth/login` | 登录获取 JWT |
| GET/POST/PUT/DELETE | `/api/v1/admin/keys` | Key 管理 |
| GET/POST/PUT | `/api/v1/admin/providers` | 提供商管理 |
| GET/POST/PUT | `/api/v1/admin/models` | 模型目录与计价 |
| GET | `/api/v1/admin/stats/overview` | 今日概览 |
| GET | `/api/v1/admin/stats/trends?range=7d` | 趋势 |
| GET | `/api/v1/admin/logs?page=&key=&model=` | 调用日志查询 |
| GET | `/api/v1/admin/billing/daily` | 每日账单 |
| POST | `/api/v1/admin/evals/datasets` | 建评测集 |
| POST | `/api/v1/admin/evals/runs` | 跑回归 |
| GET | `/api/v1/admin/evals/runs/{id}/report` | 报告 |

统一响应：`{ "code": 0, "data": ..., "message": "ok" }`；错误码表见开发规范。

## 7. 目录结构（Monorepo）

```
aegis-gateway/
├── docs/                    # 全部项目文档
├── backend/                 # Go 网关
│   ├── cmd/gateway/main.go
│   ├── internal/
│   │   ├── config/          # env/viper 配置加载
│   │   ├── model/           # GORM 模型
│   │   ├── repository/      # MySQL + Redis 数据访问
│   │   ├── service/         # 业务逻辑（route/billing/cache/...）
│   │   ├── handler/         # HTTP 处理器（代理 + 管理）

│   │   ├── billing/         # 计费与对账

│   └── go.mod
├── web/                     # Next.js 管理后台
│   ├── app/                 # App Router 页面（login/dashboard/keys/...）

```

## 8. 部署方案（本地 Docker）

```
docker-compose:
  mysql:8      (端口 3306, 数据卷持久化)
  redis:7      (端口 6379)
  gateway     (Go 二进制, 暴露 8080, depends_on mysql/redis)
  web         (Next.js standalone, 暴露 3000, 反向代理 /api → gateway)
  prometheus / grafana (可选, M5)
```
`make up` 一键启动；首次启动自动跑 migration + seed 数据（默认管理员、示例 Key、模型目录）。
